# AGENTS

## Documentation

- Decisions should be recorded in [MADR 4.0.0](https://adr.github.io/madr/) format in `docs/adrs`.
- Plans should be stored in `docs/agents/plans`.
- Keep `docs/agents/internals.md` up to date as repository changes.
- Project specifications are in `docs/specs`. Treat them as the source of truth for CLI behavior, and update them when behavior changes.
- Let's use full-length lines when writing docs.

## Development

- Commands for common development tasks (testing, linting, building) are in `Taskfile.yaml`. `task` with no arguments runs install, fmt, lint, unit and integration tests.
- The devcontainer is generated by gantry itself from `.devcontainer/gantry.yaml` (the shared [ivanklee86/devcontainers](https://github.com/ivanklee86/devcontainers) base plus `.devcontainer/gantry.libsonnet`). Edit those sources, never `devcontainer.json` directly, then run `task devcontainers`. CI fails if the committed file drifts.
- `https://github.com/ivanklee86/devcontainers` is also the reference repository for real-world overlay layouts.

## Coding standards

- Versions should always be pinned.
  - GitHub Actions are pinned to a full commit SHA with a `# vX.Y.Z` comment.
  - Tool versions in workflows use a `version: X # datasource/depName` comment, and `go install` lines in `Taskfile.yaml` use an exact `@vX.Y.Z`, so Renovate can track them (see `renovate.json`'s `customManagers`). Follow the same patterns for anything new.
- Workflows default to `permissions: contents: read`. Grant extra scopes per job, only where needed.
- `golangci-lint` (v2, `.golangci.yml`) must pass. Don't silence a finding without a `//nolint:<linter> // <reason>` comment.

### Testing

- The CLI has three tiers of tests:
  - Unit tests (test code with mocked interfaces).
  - Integration tests (use local files, pull public repositories, etc. to test isolated functions). Name them `TestIntegration_*` and gate them on `GANTRY_INTEGRATION_TESTS=1` (`task integration-test`).
  - e2e tests (call the CLI).
- CI runs unit and integration tests on amd64 and arm64, and octocov fails a PR that drops coverage below 80% or more than 0.5 points below `main`.

#### Philosophy

- Write tests that verify the *observable behavior* of this function from a caller's perspective. Each test should answer: "if this test fails, what promise to callers has been broken?"
- When designing tests:
  - First, list the test cases you plan on covering (happy path, edge cases, error handling).
  - Then write the tests.
  - Flag any behavior in the code that seems untestable or buggy rather than writing tests that enshrine it.
- Tracing and observability should be first-class citizens.
